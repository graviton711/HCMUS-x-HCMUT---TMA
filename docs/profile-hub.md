# Profile Hub — implementation contract

Approved: personal data in the Supabase Auth project; prepare migration and setup instructions. Work on `backend` for both FE/BE. Keep the existing visual system and VI/EN, light/dark support.

## User flow

- `/account`: one responsive navigation for Overview, Saved tours, Preferences, Templates, Profile and Settings. Render only the selected view; keep unsaved editor drafts while switching views. Overview contains recent/pinned searches, compact saved counts and one new-trip action. Settings groups sign-in status, browser display controls and clearly separate history/hub export/delete. No duplicated settings navigation or long stacked page. Guest history remains local; cloud features require sign-in.
- Profile edits display name plus optional phone (25 characters), home city (80) and introduction (280). These are Supabase Auth user metadata, never identity/authorization claims or inferred search constraints. Login email is read-only. Profile information is saved explicitly and remains editable after a failed request.
- Avatar: Google image when supplied by the verified provider, initials otherwise; signed-in header displays only a round avatar with an accessible account label. A user can preview/upload/remove a JPEG/PNG/WebP (up to 5 MB before browser resize). Browser produces a centered 256 px JPEG under 40 KB; BE decodes, bounds dimensions, strips EXIF and re-encodes. Private Supabase Storage bucket `profile-avatars`, fixed `<verified-user-uuid>/avatar.jpg`, owner-only RLS. Auth metadata stores only avatar choice; display uses a short-lived signed URL. Removing a custom image switches to initials. Storage failures cannot block login or erase profile edits. New migration `002_profile_avatars.sql` must be run in the Auth project; no hosted mutation is performed automatically.
- Preferences contain desired hotel stars/duration/shopping and importance levels separately. Applying preferences explicitly creates a **new structured draft**, with no dates/destination/budget/party inferred. Review and confirm are still required. Existing sessions/comparisons are immutable.
- Templates save reusable origin/destinations/adults/child count and optional preferences. Dates, prices, child ages, reference URLs and free-text conversation are excluded. Applying creates a new draft and requires current dates/budget/child ages. No silent merge into current text input.
- Save a tour from a real comparison, including those needing verification. BE binds the snapshot to the signed-in owner's comparison. Save source URL, title, supplier, selected offer/date/price, evaluation time and status. Label all saved facts historical; saving does not imply current eligibility or a booking. Recheck/compare up to five saved URLs starts a new URL draft and reruns acquisition after confirmation.
- Notes/collection labels are private. Export personal data and delete individual items/all hub data with confirmation. Search retention remains separate; bookmarks/templates survive history expiry. Account deletion is not implemented by this screen.

## Storage and API

`public.profile_hub_items` stores bounded typed documents by `(owner_id, kind, item_id)`, with per-item version and deletion tombstone. Kinds: one `preferences`, at most 40 `saved_tour`, 20 `template`. API and SQL both validate document shape, allowed keys and value bounds; direct RPC cannot store extra template dates/ages/private text. Planning documents do not use Auth metadata; the basic profile uses Auth metadata as described above. No service role or crawler/catalog mutation. SQL checks document format; a bookmark's comparison ownership is verified by the API and its historical content remains user-owned data, never fresh catalog evidence.

BE verifies Supabase identity, forwards that user's bearer plus publishable key to REST/RPC. RLS restricts reads; the atomic mutation RPC derives owner from `auth.uid()`, serializes writes per owner, checks expected version and limits, and records idempotency receipts for 24 hours. Same key/body returns the original result even after comparison expiry; changed body/key reuse and stale versions return 409. Errors never include provider credentials/raw response. Missing migration produces an actionable unavailable state; form edits remain on screen for retry.

API uses the v2 envelope: GET `/v2/profile-hub`; POST `/preferences`, `/templates`, `/saved-tours`, `/saved-tours/{id}/edit`, `/items/delete` under that prefix. Mutations require `Idempotency-Key` and `expected_version`; the UI generates stable UUIDs for new templates; saved IDs are derived from canonical URL. Export uses GET state. Cloud state is discarded on account switch/sign-out; no personal hub data in browser persistent storage. A conflict preserves unsaved edits. Reload is explicit; in a delete dialog it closes the stale confirmation and requires choosing the current item again. Comparison selection counts only currently saved items.

## Ranking

Importance levels do not create a preference by themselves. Applying the explicit “prefer lower listed tour price” choice adds a separate soft `estimated_cost prefer_low` budget with the same currency/basis/coverage as the trip's listed hard budget and a scale equal to its cap. It keeps hard filtering intact. Utility is `1 / (1 + listed_price / cap)`, using the selected offer's fresh applicable price, with evidence; unavailable prices remain unknown. The price is not payable total. Pace/culture levels can be saved but are labelled unsupported for ranking. No feedback inference from clicks.

## Verification and setup

Test ownership, CAS races/retries, capacity, migration unavailable, snapshot binding, historical save and template reset. FE checks explicit application, no implicit hard constraints, retained edits on errors, user-switch isolation, responsive VI/EN and keyboard access. SQL migration is supplied for the **Auth** Supabase project; do not run against the crawler schema automatically. See `examples/profile-hub-supabase.md` for configuration and cloud verification.
