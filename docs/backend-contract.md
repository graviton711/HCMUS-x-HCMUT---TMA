# Hợp đồng backend

API HTTP cho frontend và các consumer. Schema live ở `/openapi.json`; models trong `src/backend/models.py` là nguồn chuẩn duy nhất. Frontend gọi contract này, không gọi `/v2` legacy và không đọc database trực tiếp. Hội thoại tự do do provider agent điều khiển; backend tools nhận dữ liệu cấu trúc và kiểm tra trước khi đọc catalog. Public `/agent/*` JSON/SSE giữ nguyên khi provider đổi.

## Current runtime

- A comparison includes `decision_trace`: scanned tour/offer counts, hard-condition state counts, a sequential offer funnel, and first-blocker counts. Per-condition totals may overlap because one offer can fail or remain unknown on several conditions; `unknown` is never counted as `fail`.
- `GET /comparisons/{id}/eliminated?limit=&cursor=` returns owner-scoped, paginated excluded offers with each hard condition's `pass`/`fail`/`unknown` evaluation and reason. Trace counts are computed from the full scan before agent/UI response trimming.
- The scan retains a lightweight index for every scanned offer plus full source detail for hard-pass and displayed near-miss tours, in an owner-scoped runtime record keyed by comparison ID. The user-facing comparison remains bounded. A scenario that admits a previously unhydrated tour loads its detail by stable source key and checks source observation timestamps against the retained index; changed source data requires rerunning the baseline. Legacy comparisons without a retained snapshot report drill-down and what-if as unavailable and can be rerun. No SQL schema migration is required.
- `POST /comparisons/{id}/scenarios` compares a criteria or cost-assumption scenario against the retained scan snapshot and returns deltas without changing the source comparison. Criteria changes are returned as a proposal to copy into the Brief for user review; cost assumptions remain scenario-local. A scenario may only publish newly admitted tours after their soft evidence has been evaluated; otherwise those metrics remain explicitly unknown.
- Each selected option carries metric comparisons against the eligible reference group, including value, unit, currency/scope, state, and evidence. Metrics are compared only when dimensions match; missing values remain unknown.
- A requirement may contain common `conditions` and `alternatives`. Common conditions are ANDed; each alternative is an AND group; a candidate is eligible when the common conditions pass and at least one alternative group passes. Empty `alternatives` preserves the legacy all-conditions-AND behavior. Alternative IDs and condition IDs are unique within the requirement.
- Departure-date ranges use inclusive ISO `date_from`/`date_to` bounds; an exact departure day uses the same date for both bounds. These fields bound the tour's recorded departure date; they do not verify a return date. Fuzzy ranges are shown as editable assumptions. The nearest future year is interpreted in `Asia/Ho_Chi_Minh`; late month means days 21 through month end. One distinct `(quote,date_from,date_to)` window is a single shared assumption that may link date pairs across branches; the UI groups display by this tuple. Editing one branch of a shared assumption splits it: the edited pair becomes its own assumption, the rest stay linked.

- `GET /health` → `{status, version}`.
- `POST /sessions` → guest session Bearer token with expiry. Only a SHA-256 token hash is persisted.
- `GET /catalog` → `{destinations}` from the active read-only catalog provider; this is a basic lookup, not the richer frontend catalog contract.
- `POST /requirements` — body `{conditions, alternatives?, assumptions?, raw_text?, travelers?, ranking?}` để lưu requirement có cấu trúc, hoặc `{form}` cho workspace hiện tại → `{requirement}`. Text tự do không được parse thành điều kiện; field/operator/value sai bị từ chối.
- `GET /requirements/{id}` → requirement đã lưu.
- `POST /comparisons` — body `{requirement_id, candidate_limit?}` → `{comparison}` gồm xếp hạng, hard evaluations, evidence, phân tích và snapshot candidate tự chứa để kết quả đã lưu vẫn render được. Endpoint này dùng `candidate_default` (hiện là 20) và giới hạn `candidate_max` (hiện là 100). Agent MCP quét catalog đến `data.scan_limit` (hiện là 2000 theo `configs/settings.yaml`); số bản ghi quét không khẳng định tổng số tour trong database. `ranked` chỉ chứa offer qua hết điều kiện cứng; `near_miss` chứa offer fail không quá `near_miss_max_fails` điều kiện cứng (mặc định 2), xếp theo pass nhiều → fail ít → giá rẻ để UI render nhóm "Gần đạt" riêng. `unknown` không tính là fail. `tour_snapshots[].detail_state` là `complete` khi có dữ kiện nguồn dài hoặc `index` khi chỉ giữ trường dùng để lọc; consumer không được suy ra ưu/nhược từ trường văn bản rỗng ở snapshot `index`.
- `GET /comparisons/{id}` → comparison đã lưu.
- `GET /history?limit=&cursor=` and `GET /history/{id}` → cursor pagination and owner-scoped requirement/comparison detail for guest sessions.
- `POST /agent/sessions` — Bearer bắt buộc; tạo local agent session và trả `{agent_session_id}`.
- `POST /agent/sessions/{id}/messages` — Bearer bắt buộc; body `{message}`. Có thể trả `{assistant_text, choices?, tool_calls?, requirement?, comparison?, decision_draft?}`. Khi cần gợi ý địa điểm, agent dùng `catalog_facets` và một lần `discover_destinations` để kiểm tra các điều kiện chung/các nhánh còn mở; không yêu cầu người dùng chọn một phương án đã nói là linh hoạt. Tool preflight so ngày khởi hành có trong offer trực tiếp với khoảng ngày yêu cầu, không phụ thuộc tuổi crawl; ngày thiếu/không hợp lệ là unknown. Ngày khớp không xác nhận còn chỗ hay nhà cung cấp vẫn mở bán. Preflight không tạo comparison, không xác nhận sức chứa nhóm. Một `decision_draft` chứa requirement đã cấu trúc; việc tạo draft không chạy comparison. Với `Accept: text/event-stream`, trả SSE `progress`, từng lần gọi `tool` có mô tả nghiệp vụ và trạng thái, rồi `result`; lỗi giữa stream dùng event `error`. `tool.status=error` chỉ nói lần gọi đó lỗi; lượt vẫn có thể kết thúc thành công nếu agent gọi lại và trả kết quả hợp lệ. Nếu tool lỗi và agent không có nội dung khác để trả, backend gửi lời nhắc thử lại; phản hồi OpenCode rỗng hoàn toàn vẫn là lỗi `OPENCODE_RESPONSE_EMPTY`.
- `POST /agent/sessions/{id}/decisions` — Bearer bắt buộc; body chứa requirement đã được người dùng review, gồm `conditions`, tổng `travelers`, `traveler_mix` tùy chọn (`adult`, `child`, `small_child`, `infant`) và cho từng soft condition một trong hai: `weight_percent` (tổng 100) hoặc `priority` (`low`/`medium`/`high`, materialize theo bậc thang 1:3:9, điều kiện thiếu priority mặc định `medium`). Nếu có mix, tổng nhóm tuổi phải bằng `travelers`; thiếu mix thì không suy ra tổng giá theo nhóm. Backend validate lại schema, hard conditions và tổng trọng số đúng 100 trước khi chạy. MCP ghi Comparison hoàn tất vào runtime store theo mã lượt riêng; backend lấy, kiểm tra requirement rồi mới lưu theo owner và trả response/SSE. Kết quả cuối không phụ thuộc model có nhắc lại JSON tool trong câu trả lời hay không. Response trả `metric_profiles`, `decision_options`, `decision_views`, `ranked`, `near_miss`, evidence và `candidates_considered`.

`decision_draft` và `comparison` là artifact có cấu trúc, được UI hiển thị riêng trong Decision Workspace. Decision Brief giữ các nhánh lựa chọn, date assumptions và điều kiện dùng chung để người dùng review; không cần chốt một địa điểm trước khi có brief. `assistant_text` chỉ nên hướng dẫn ngắn về trạng thái/hành động kế tiếp; không lặp lại toàn bộ điều kiện hoặc bảng kết quả. Văn xuôi không thay thế artifact hợp lệ.

Local agent ID ánh xạ tới `codex_thread_id` hoặc `opencode_session_id` theo guest owner; ID provider không lộ ra client. Các lượt tìm kiếm giới hạn số tour hiển thị theo contract, nhưng đánh giá soft bao phủ mọi hard-pass candidate trong phạm vi catalog scan. MCP dùng batch để không gửi toàn bộ evidence cùng lúc vào model context.

Requirements/comparisons created without a Bearer token remain unowned for workspace compatibility. When a guest Bearer token is supplied, reads and history are restricted to that session. Existing unowned records are preserved by the schema migration. `POST /comparisons` runs synchronously. Agent routes require a Bearer session and never accept owner IDs from the client. The local default is Codex through `CODEX_SERVER_URL`; `AGENT_PROVIDER=opencode` retains the current Render provider until hosted eligibility is confirmed. Ordinary requirement/comparison routes do not depend on either agent.

## Provider event adapters

The Codex gateway receives `POST /turns` with `{message, thread_id?}` and streams Codex JSONL. The backend maps thread IDs, MCP lifecycle/results, assistant messages, token usage and terminal errors into the existing agent event model. The gateway loads `configs/prompts/backend-agent.yaml`, enables only MCP `tour-catalog`, disables shell and multi-agent tools, and uses a read-only sandbox. Local development pins Codex CLI `0.162.1`; `CODEX_SERVER_URL` configures the gateway and `AGENT_PROVIDER` selects `codex` or `opencode`.

The OpenCode adapter remains available for the Render deployment while hosted ChatGPT plan eligibility is reviewed. OpenCode JSON events may expose MCP calls directly or wrap them in Code Mode `execute`. The backend normalizes wrapped tool names and inputs from `state.metadata.toolCalls`, then parses returned JSON from `state.content`. SSE progress and `tool_calls` represent the logical MCP operations; wrapper-level argument errors such as a missing `code` field are not reported as failed catalog operations. A Decision Brief is returned only from a validated `draft_requirement` payload.

## Agent ranking

Metric extraction explicitly reports which source fields were reviewed: itinerary, route, inclusions, exclusions, surcharges, cancellation_policy, or child_policy. Only a non-empty source field named in that report counts as reviewed; an empty fact list never means exclusions contain no extra costs.

Requirement draft mang điều kiện `hard`/`soft`; mỗi soft condition có `weight_percent` hoặc mức `priority` (thấp/vừa/cao) — có priority thì hệ thống tự tính % theo bậc thang 1:3:9. Draft chỉ được chạy khi tổng trọng số bằng 100. Hard conditions quyết định eligibility. Trước khi brief được duyệt, `discover_destinations` lọc catalog theo hard conditions đã biết; đây chỉ là preflight.

Sau khi xác nhận, `query_tours` đọc index nhẹ của toàn scan và áp hard filter trước; chỉ tải các trường dài cho mọi hard-pass candidate và near-miss được giữ lại. Metric enrichment xử lý riêng từng trường mềm trên mọi hard-pass candidate. Structured fact phải có quote khớp nguồn; numeric/categorical values được chuẩn hóa và tính bởi code. Cache enrichment theo content hash và extractor version. MCP lưu comparison cuối qua `decision_run_id`; tool progress không phải kênh bàn giao kết quả.

Mỗi response comparison bổ sung `metric_profiles`, `near_miss_profiles`, `decision_options` và `assumptions`, đồng thời giữ `ranked`, `near_miss` và snapshots cũ. Metric fact gồm metric key, value/range, unit, state, source field, exact quote, observed time và method version. Exclusion được phân loại bắt buộc/tùy chọn/có điều kiện; chỉ khoản có amount/unit rõ mới cộng vào cost.

Metric/objective views: `cheapest` (exact group total, same currency), `best_fit` (weighted score/range và evidence coverage), `experience_rich`, `fewest_legs`, `cancellation_flexible`, `included_value` và `balanced` (Pareto trên các metric có thể so sánh). Metric thiếu dữ liệu thì view đó unavailable hoặc nêu rõ coverage; không tạo overall score ẩn. Mỗi view tối đa 5 candidates. Toàn result phải có ít nhất ba tour thật khác nhau nếu scan có đủ; views có thể dùng chung candidate nhưng không thay tiêu chí distinct tour.

`candidates_considered` là số tour đã quét, không phải tổng catalog. `ranked`/`near_miss` và các tool `ask_choice`, `catalog_facets`, `discover_destinations`, `draft_requirement`, `tour_detail`, `clarify_date` vẫn tương thích. Thay brief/trọng số để chạy what-if tính result mới, không ghi đè comparison cũ. Không tự nới điều kiện; nếu thiếu ba tour, trả số thực có và kịch bản nới điều kiện cần user review.

## Remaining integration target

- `/auth/*` → Supabase Auth adapter; backend verify identity với đúng provider project, không tin owner ID từ client.
- `/requirements/{id}/revisions/{revision}`, `/requirements/{id}/proposals`, `/proposals/{id}/*` → revision, draft proposal, confirm/cancel/discard explicit.
- `POST /comparison-jobs`, `GET /jobs/{id}`, `GET /jobs/{id}/events`, `POST /jobs/{id}/cancel` → progress có thứ tự và trạng thái terminal; không đổi kết quả comparison đồng bộ hiện có.
- `/history/*` → rename/pin/archive, transcript, metadata CAS và guest-session linking explicit (basic list/detail are runtime).
- `GET /comparisons/{id}/eliminated` and `POST /comparisons/{id}/scenarios` are runtime APIs as described above. A durable scenario history/proposal resource is not implemented; applying criteria still requires editing and confirming the Brief.
- `/evidence/*`, `/requirements/{id}/messages/*`, `/contacts` → evidence lookup, conversation follow-up và contact ticket.

Lỗi HTTP dùng `{error: {code, message}}`; SSE dùng event `error` với `{code, message}`; MCP trả cùng envelope JSON trong tool content. `code` ổn định để consumer map ngôn ngữ hiển thị; `message` là tiếng Anh. Lỗi 4xx thông thường không được log. Lỗi 5xx hoặc retryable được log một lần tại ranh giới transport với metadata an toàn; lỗi kết nối catalog bổ sung operation, thời lượng, loại exception và SQLSTATE nếu có, không ghi exception text/DSN. Exception không dự kiến trả `INTERNAL_ERROR` chung, không lộ nội dung exception. Agent không có deadline tổng; tiến trình kết thúc khi provider hoàn tất hoặc client ngắt kết nối. Timeout riêng của MCP tool và kết nối dữ liệu vẫn áp dụng.

Thiếu dữ liệu là `unknown`, không tính là đạt. Destination chỉ gồm nơi tham quan đã bỏ origin endpoint khi endpoint trùng sau chuẩn hóa tổng quát; route/raw vẫn được giữ. Snapshot không chứa country alias hay completeness metadata. Agent ánh xạ quốc gia/vùng sang các label thực có trong `catalog_facets`, và hỏi lại nếu không tìm được nhãn phù hợp. Engine chỉ so điều kiện destination tường minh với các label đó. Với ngân sách, mọi giá offer dạng số có currency được so như giá công bố, không phụ thuộc metadata `fixed`/`from`/`contact`/`unknown`; giá thiếu hoặc không có currency là unknown. Giá công bố không cam kết tổng tiền cuối cùng; exclusions và phụ phí có nguồn được trình bày riêng. Demo mặc định coi bản ghi có timestamp crawl hợp lệ là snapshot mới nhất hiện có, không tự hết hạn theo thời gian; timestamp vẫn hiển thị và không xác nhận chỗ trống trực tiếp. Có thể bật TTL dương để đánh dấu dữ kiện ngày khởi hành đã cũ. Soft scoring chỉ nhận tour còn offer qua hard filter, quote phải khớp nguyên văn evidence; unknown tạo khoảng điểm hoặc trạng thái chưa so sánh được.

## Pipeline

Codex local (OpenCode trên Render đến khi đủ điều kiện) điều khiển hội thoại → MCP tools kiểm tra điều kiện có cấu trúc qua `input` → workflow lấy catalog và hard-filter → agent trích structured facts có quote → code xác minh, chuẩn hóa và tính metric profiles → `decide` tạo objective views/options. Không còn free-text keyword/NIM extraction hay slot state machine. Chi tiết: [system-architecture](system-architecture.md), [`src/backend/README.md`](../src/backend/README.md), [`src/backend/agent/README.md`](../src/backend/agent/README.md).

## Chạy tối thiểu

```powershell
uv sync
corepack pnpm --dir src/frontend dev:all
```

Mặc định local dùng SQLite cho runtime store. Catalog luôn là Supabase chỉ-đọc qua `SUPABASE_TOUR_DB_URL` (thiếu URL thì báo `CATALOG_NOT_CONFIGURED`); không cần `DATABASE_URL`. Migration `migrations/004_runtime_store.sql` phải được áp dụng trước; session mapping dùng records store.

`dev:all` khởi chạy backend, Codex gateway (`4099`) và web. Gateway gọi Codex CLI `0.162.1` với `--json` theo từng tin nhắn, dùng `codex.model=gpt-6-luna` và `codex.reasoning_effort=medium`, rồi resume bằng thread ID; MCP `tour-catalog` là công cụ duy nhất, shell và multi-agent tắt, sandbox chỉ đọc. Nếu CLI chưa đăng nhập, gateway khởi chạy device-code flow nền và ghi URL/mã xác thực vào log. Render hiện giữ `AGENT_PROVIDER=opencode`; chỉ đổi sau khi xác nhận app remote-hosted đủ điều kiện dùng ChatGPT plan. Render free xóa filesystem khi spin down/redeploy, nên sau đó cần đăng nhập lại. Nếu Codex báo thread ID cũ không còn, backend xóa mapping lỗi; lần gửi lại mở thread mới. Survey tiếp tục dùng OpenCode CLI cùng `opencode.model`. Frontend nhận tiến độ tool qua SSE và kết quả cuối cùng qua event `result`; consumer cũ vẫn dùng JSON mặc định. Trang chào: `http://127.0.0.1:8000/`, docs tương tác: `http://127.0.0.1:8000/docs`.

## Operational logging

Operational logs are not part of the HTTP/SSE contract. Each request has a correlation ID returned in `X-Request-ID` and included in backend log records. Provider diagnostics record process status and bounded, filtered stderr only on failure; tool logs use logical tool name and status without inputs or outputs. The Codex gateway writes device-code login URL/code to its own logs for operator authorization. A validated Decision Brief is logged as a boolean lifecycle milestone, not with its contents. Local file logging defaults to `.local/logs/backend.log` and rotates at 10 MiB × 5 backups; hosted Render deployments use the Dashboard log stream and do not rely on container files.
